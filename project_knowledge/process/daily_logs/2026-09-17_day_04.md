# Day 4 — Project Re-entry Brief Prototype

## Status

**Done**

## Aim

My aim today was to translate the research direction of ProjectOS into a small but testable technical structure.

Instead of developing a general file-chat interface, I focused on a more specific interaction: a Project Re-entry Brief that could help a creative practitioner reconstruct the state of a long-term project after an interruption.

The prototype needed to remain source-grounded and avoid presenting generated interpretations as facts.

## Planned work

The main tasks were:

1. define the structure of the Project Re-entry Brief;
2. implement the six-section brief as a command-line prototype;
3. test how category-aware retrieval affected the selected evidence;
4. record retrieval limitations;
5. add automated structural tests.

## Completed work

### 1. Defined the Re-entry Brief schema

I documented the design of the brief in:

`project_knowledge/decisions/design_decisions/dd_002_reentry_brief_schema.md`

The brief contains six sections:

1. Current intention
2. What changed and why
3. Current versus superseded directions
4. Relevant feedback
5. Unresolved tensions
6. Possible next action

Each section has its own retrieval question and relevant document categories.

I also separated two different forms of status:

- `evidence_status`, describing whether supporting evidence was retrieved;
- `review_status`, describing whether the user has reviewed the reconstruction.

This distinction is important because retrieved evidence should not automatically be treated as an accepted interpretation of the project.

### 2. Implemented the command-line prototype

I created:

`src/reentry_brief.py`

The script:

- loads the Echo Field sample project;
- divides the documents into chunks;
- creates embeddings;
- runs a separate query for each brief section;
- selects up to two evidence chunks;
- displays the source, category and chunk identifier;
- displays the semantic similarity score;
- sets the default review status to `unreviewed`;
- and avoids generating unsupported project summaries.

The prototype successfully loaded:

- 4 documents;
- 12 chunks;
- and 6 Re-entry Brief sections.

### 3. Compared two evidence-selection approaches

The first version attempted to include evidence from different preferred source categories.

For example, if a section allowed both `feedback` and `process`, the system attempted to select one result from each category.

This increased source diversity but introduced weak evidence.

In the Relevant Feedback section, a process chunk with a similarity score of `0.1277` was selected even though a more relevant feedback chunk was available.

In the Possible Next Action section, a weak process result with a score of `0.1106` was also selected.

I changed the evidence-selection rule so that:

1. results from irrelevant categories are removed;
2. the original semantic ranking is preserved;
3. the two strongest eligible results are selected;
4. category diversity is not forced.

After this change:

- the second Relevant Feedback result improved from `0.1277` to `0.3399`;
- the second Possible Next Action result improved from `0.1106` to `0.1617`;
- and the change-and-rationale section selected two directly relevant decision chunks.

The comparison was recorded in:

`outputs/test_results/day_04_reentry_brief_results.md`

### 4. Identified an important retrieval limitation

The revised version improved several sections, but it also exposed a more important limitation.

For the Unresolved Tensions section, the system selected tutor-feedback chunks with relatively high similarity scores. However, one of these chunks described feedback that had already been addressed.

At the same time, the retrieval system missed a lower-scoring chunk that explicitly contained a `Current blockers` heading.

This means that the system could identify text that was semantically related to problems or limitations, but it could not reliably distinguish between:

- a current blocker;
- historical feedback;
- an implemented response;
- a superseded direction;
- and future work.

This was not simply a ranking error. It showed that semantic similarity does not represent project-state accuracy.

### 5. Added automated structural tests

I created:

`tests/test_reentry_brief.py`

The tests verify that:

- exactly six sections exist;
- the section order remains correct;
- only eligible source categories are selected;
- no section contains more than two evidence items;
- evidence contains a source and chunk identifier;
- missing evidence is represented as `insufficient`;
- and every section begins with the review status `unreviewed`.

The final test result was `6 passed in 6.09s`.

The tests use simulated retrieval results and therefore do not need to load the embedding model.

## Problems encountered

The main problem was that document category and semantic similarity did not fully represent the lifecycle of project evidence.

A chunk could be highly similar to a retrieval question while still describing:

- an old project state;
- feedback that had already been implemented;
- or an issue that was no longer active.

I also found that forcing evidence diversity could reduce relevance by including weak results from secondary categories.

## What I learned

The most important finding today was:

> A higher semantic similarity score does not necessarily mean that a chunk is a more accurate representation of the current project state.

A standard RAG pipeline can retrieve related text, but project re-entry requires additional distinctions between current, historical, resolved, unresolved and superseded information.

This finding strengthens the research justification for ProjectOS.

The value of the system is not simply that it can search project files. Its research focus is how retrieved evidence should be structured, reviewed and corrected when reconstructing a long-term creative project.

## Reflection

Today’s prototype helped move ProjectOS away from being a generic AI productivity tool.

The six-section structure gives the system a specific interaction purpose: helping a user return to a creative project and inspect the evidence behind the reconstructed state.

The retrieval failures were useful rather than purely negative. They exposed where a generic semantic search system is insufficient and suggested why user review must be part of the interaction.

The prototype currently retrieves evidence but does not claim to understand the project completely. This is appropriate for the current stage because it keeps the limits of the system visible.
