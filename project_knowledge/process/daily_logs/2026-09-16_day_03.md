# Day 3 — Building the Retrieval Baseline

## Main objective

My objective today was to test whether ProjectOS could retrieve relevant evidence from a small collection of long-term creative project documents.

I treated this as an Iteration 0 technical feasibility test rather than the first formal design iteration. The aim was to establish a transparent retrieval baseline before adding an interface, a vector database or an answer-generating language model.

## Planned work

* Configure a working Python environment.
* Create a small demonstration project corpus.
* Load and divide project documents into searchable chunks.
* Generate semantic embeddings.
* Retrieve the three most relevant chunks for a project question.
* Evaluate the retrieval pipeline with several fixed questions.
* Record the technical results and reflect on their implications.

## Work completed

### 1. Development environment

I created and activated a dedicated Conda environment named `projectos`, using Python 3.11.16.

The initial setup was complicated by a PowerShell execution-policy restriction. This prevented the Conda PowerShell profile from loading correctly. I resolved the issue by using Command Prompt to activate the environment and then explicitly selecting the ProjectOS Python interpreter in VS Code.

I installed the initial dependencies:

* NumPy;
* pypdf;
* sentence-transformers;
* pytest.

### 2. Demonstration corpus

I created a controlled demonstration corpus based on my previous Echo Field creative computing project.

The corpus contains four Markdown documents:

* `current_state/goals.md`;
* `decisions/design_notes.md`;
* `feedback/tutor_feedback.md`;
* `process/project_log.md`.

These documents represent different forms of project knowledge that may become difficult to reconnect during a long-term creative project.

### 3. Document loading

I implemented `src/document_loader.py`.

The loader recursively finds supported files and extracts their content while retaining:

* source path;
* document category;
* file type.

The loader currently supports Markdown, text and PDF files. All four Echo Field demonstration documents were loaded successfully.

### 4. Document chunking

I implemented `src/chunking.py`.

The documents were divided using:

* a maximum size of 120 words;
* an overlap of 30 words;
* a unique identifier for every chunk.

The four source documents produced 12 chunks. Each chunk retained its original source and category.

### 5. Semantic retrieval

I implemented `src/retrieval.py` using the `all-MiniLM-L6-v2` sentence-transformer model.

The system:

1. converts each document chunk into a normalised embedding;
2. converts the user’s question into an embedding;
3. calculates semantic similarity;
4. ranks the chunks;
5. returns the three most relevant pieces of evidence.

The first test question asked why hand tracking had been replaced with whole-body movement. The first two results came from the design decision document and contained both the technical problem and the design rationale.

### 6. Retrieval evaluation

I created six fixed evaluation questions covering:

* design decisions;
* current interaction state;
* tutor feedback;
* movement-strength values;
* multiple participants;
* user-testing problems.

The results were:

| Metric |        Result |
| ------ | ------------: |
| Hit@1  |  4/6 — 66.67% |
| Hit@3  | 6/6 — 100.00% |

The expected source appeared within the first three results for every question.

## Problems encountered

The first problem was the Python and Conda configuration on Windows. The Windows Store Python alias was visible, but it was not a usable Python installation. Conda was installed but unavailable as a normal PowerShell command because the PowerShell profile could not run.

I resolved this without changing the system-wide execution policy by activating the environment through Command Prompt and selecting its Python executable directly in VS Code.

The Hugging Face model download also displayed a warning about Windows symlink support and unauthenticated requests. These warnings did not stop the model from downloading or running, so I did not make unnecessary system changes.

## Reflection

Today’s result demonstrates that the basic technical idea behind ProjectOS is feasible. A small semantic-retrieval pipeline can identify relevant evidence across different forms of creative-project documentation.

However, the evaluation also showed that retrieval quality cannot always be judged using one expected file. For two questions, another relevant document ranked above the predefined source. This happened because creative-project knowledge is often repeated or interpreted across decisions, feedback, process logs and current-state summaries.

This is important for the design of ProjectOS. The tool should not treat every retrieved passage as equivalent. It needs to help the user distinguish between:

* current state;
* historical process;
* confirmed decisions;
* external feedback;
* unresolved questions;
* superseded directions.

I also learned that a simple and visible implementation is useful at this stage. Adding an LLM immediately might have produced more impressive-looking output, but it would have made it harder to determine whether the underlying evidence was correct.

The current system proves retrieval feasibility, but it does not yet prove that ProjectOS supports reflection, creativity or project re-entry. Those claims will require a structured re-entry experience and later user evaluation.

## Decisions made

* Retain the current configuration as the Iteration 0 baseline.
* Keep Top 3 evidence visible rather than returning only one passage.
* Do not optimise the system only to improve the six existing test questions.
* Do not add LangChain or a vector database until an observed need justifies them.
* Keep retrieval separate from language-model generation during the baseline stage.
* Use source role and project status as part of the future re-entry experience.
